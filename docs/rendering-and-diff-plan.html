Pandia · Architecture Plan

Removing Pandia's Ceilings

Three hard limits sit between Pandia and "open anything." None of them are rendering limits. This is what each one actually is, and how it comes down.

Written 17 Aug 2026 Against v1.0.5 Diff algorithm: benchmarked, decided Rendering & mmap: proposed

Part 01The three ceilings

Pandia advertises that it opens files of any size. It doesn't, and the reasons are all different from each other.

2 GB document.rs:32 — MAX_DOC_BYTES

Any file above this is refused outright. Caused by reading the whole file into a heap String.

3 MB InlineDiffView.svelte:32 — INLINE_MAX

Inline diff refuses to run. Caused by materialising both documents in JavaScript before drawing.

4M cells linediff.ts:17 — LCS_CELL_CAP

Above this the diff silently emits a fake result: every left line deleted, every right line added. Measured to fire on a 154 KB file.

The fake diff is the urgent one

The other two ceilings refuse to do the work and say so. This one does the work wrong and says nothing.

src/lib/views/compare/logic/linediff.tsLines 26–31 
if (A * B > LCS_CELL_CAP) {
  return [
    ...a.map((text) => ({ type: 'del', text })),   // every left line
    ...b.map((text) => ({ type: 'add', text })),   // every right line
  ];
}

fullRows() trims the common head and tail before the table is built, so the cap is evaluated against the changed middle rather than the whole file. That detail turns out to be the entire story, and not in the way you would guess.

The trigger is edit spread, not file size

Prefix and suffix trimming can only remove the head before the first change and the tail after the last one. Everything between them survives. So two edits at opposite ends of a document defeat trimming exactly as thoroughly as a thousand edits do.

Measured across the benchmark fixtures, on one identical 500-element array — a 154 KB file:

Edit pattern Post-trim cells Result
One value changed 1 Fine
200-line block inserted 0 Fine
12 edits scattered through the file 54,066,609 Fake diff
30% of lines changed 62,015,625 Fake diff

A single deep edit is free, because trimming strips everything around it. Twelve scattered edits in a 154 KB file produce a fabricated diff. File size barely matters.

What the user is actually shown

Fixture Size Lines truly changed Lines reported
array-500-scattered 154 KB 24 14,706
config-20k-scattered 427 KB 24 35,330
array-50k-scattered ~100 MB 24 1,466,726

Eight of the thirty-two benchmark fixtures produce a fabricated diff. None of them warn.

Root cause

The algorithm is a dense Longest Common Subsequence table: O(A×B) time and O(A×B) memory. At the cap that's 2,001 separate Uint32Arrays totalling about 16 MB. The cap exists because the algorithm has no other way to stay bounded — and note that the fake path is also the fastest path, at 0.9 ms, because giving up costs nothing. Any benchmark measuring only time would rank this behaviour as the winner.

Why virtualization doesn't lift the 3 MB ceiling

Virtualization governs what gets drawn. It says nothing about what gets loaded. The inline diff loads everything before it draws anything:

src/lib/views/compare/components/InlineDiffView.svelteLines 97–101 
docGetValue(l, [])              // 1 — whole JSON value crosses IPC into JS
stringifyWithOffsets(lv).text   // 2 — whole document as one string
leftText.split('\n')            // 3 — an array holding every line

Three full copies of both documents in the JavaScript heap before the first row is painted. INLINE_MAX exists to stop that from killing the process.

There is a fourth cost that isn't obvious. In V8, split() produces sliced strings that keep a pointer to the parent they came from. Every one of those line strings pins the entire document text in memory. Pierre hit exactly this and named it — detaching parsed strings took their Linux kernel diff from 2.4 GB to 1.15 GB, with parse time down about 80%.

Part 02Fixing the diff

Move the line diff into Rust. Every ceiling in Part 01 except the 2 GB one dissolves as a side effect.

Rust already holds the parsed document. src-tauri/src/doc/diff.rs already exists and already does a structural JSON diff. What it doesn't do is line diffing — that's why the work ended up duplicated in JavaScript against a text rendering of the same data.

What the benchmark measured

Five candidates against 32 fixtures across four JSON shapes, each combination run in a child process so a crash records as a result rather than killing the run. Peak heap comes from a tracking global allocator, not sampling. Harness and fixture generator live in src-tauri/benches/json_linediff/; fixtures regenerate byte-identical.

Time, on fixtures where the current code does real work

These are the honest comparisons. Fixtures where the cap fired are excluded, because a fabricated diff isn't the same job.

On that last row the JavaScript implementation spent 328 MB to produce a fabricated result. INLINE_MAX exists to contain exactly this.

The candidate that settles the argument

similar with Algorithm::Lcs is our current algorithm, written in Rust. It peaked at 3.3–3.9 GB on 32,000-line fixtures and hard-crashed on all four 10k and 50k scattered and heavy arrays — allocation abort, not a timeout.

Rust does not rescue the dense table. The problem was never the language.

Result

156 ok · 0 degraded · 0 fake · 4 crashed, all four similar-lcs. No Rust candidate reproduced the fabricated-diff failure mode on any fixture.

Histogram or Myers

Histogram is a heuristic and does not guarantee a minimal diff. That looked like a real tradeoff until it was measured: across every fixture, histogram's worst over-report was +64 lines out of 410,488 — 0.016% — while running 2.7× faster than Myers on that same input.

Fixture histogram myers similar-myers similar-patience
array-50k-heavy 108 ms 291 ms 1,386 ms 16,504 ms
array-50k-scattered 43 ms 49 ms 170 ms 183 ms
array-10k-heavy 19.2 ms 58.9 ms 234 ms 794 ms

Take histogram. Keep imara-myers reachable behind a flag if a guaranteed-minimal diff is ever wanted; nothing in the data justifies paying for it by default.

  1. Adopt imara-diff, histogram

    Decided by the benchmark above, not by reputation. It is O(N·D) in the number of differences rather than O(N²) in document size, which is the whole ballgame for JSON, where edits are usually small relative to file size.

    It diffs an 800,000-line pair — 640 billion cells by the old measure, 160,000× past the JavaScript cap — in 43 ms using 47 MB, with correct counts. The 4M cell cap has no equivalent and simply goes away.

    deletes LCS_CELL_CAP Cargo.toml doc/diff.rs

  2. Return hunks, not rows

    The current IPC hands JavaScript a complete UnifiedRow[] covering the whole document. Replace it with a command that returns hunk descriptors only — line ranges and change kinds, no text.

    A 20,000-line document with four small edits becomes four hunk records instead of 20,000 row objects. The frontend then asks for line text by range, for the range it's about to paint.

    deletes INLINE_MAX new IPC command compare/state

  3. Add word-level intra-line diff

    This is the feature JSON needs most and currently lacks entirely. Today, changing one value in a long line renders as a whole-line delete plus a whole-line add, and the reader has to spot the difference by eye.

    Run it only on paired delete/add rows, and only on rows inside the visible window. It is far too expensive to run across a whole document and completely cheap across forty lines.

    new capability visible-window only

  4. Delete linediff.ts

    Once hunks come from Rust, diffMiddle, fullRows and the DP table have no callers. emitContext and changeAnchors are presentation logic and stay — they operate on hunks, which are now small.

    linediff.test.ts should be ported to Rust rather than dropped. Its cases are good and they'll catch algorithm swaps.

    −189 lines JS port tests to Rust

Two shapes a better line algorithm does not fix

The benchmark was built expecting minified and reformatted JSON to be slow or to blow up. Neither happened, and what it found instead read, at the time, as a hole in the plan. One thing to hold onto: these numbers were measured on raw file text, because raw file text was what the app diffed. That premise is the part that did not survive implementation.

Shape Fastest candidate What the diff says Is that useful?
Minified, 20 MB on one line 2.6 ms 1 hunk, 2 changed lines No — the whole file is one delete plus one add
Pretty ↔ minified, same data 0.3 ms 100% of lines changed No — and yet it is literally correct

Every candidate handles both in milliseconds. Nothing hangs, nothing allocates, and the quality verdict comes back clean — because at the line level these answers are the truth. A 20 MB document that is one line genuinely has one changed line. A reformatted file genuinely has every line changed.

The model is wrong, not the algorithm. Line diffing cannot say anything useful about a document whose line structure carries no meaning.

Superseded

This section originally prescribed detecting both shapes at diff time and routing them to the structural diff in src-tauri/src/doc/diff.rs. That prescription is obsolete, and the reason is worth being honest about: the implementation revealed the premise was wrong. The shipped doc_diff_lines never diffs raw file text. Both documents render through Document::canonical_lines — the byte-identical Rust port of the JS renderer, built so hunk coordinates match what CodeView paints — and the diff runs over that canonical pretty text. Pretty-printing first dissolves both shapes as a side effect: a minified document diffs as its expanded rendering, and a minified/pretty pair of the same data canonicalises to identical text and yields zero hunks. The numbers above stay in the record — they are still true of raw-text diffing, and they are why the fixture set included these shapes — but no such text reaches the diff anymore. The diff_lines_* tests in src-tauri/src/commands.rs hold the invariant.

Canonicalisation moved the cost rather than deleting it. A lazy document — 10 MB and up — holds no parsed value to render, so canonical_lines parses the entire root into a serde_json::Value and pretty-prints it: one full value tree plus one full canonical string per side, cached per document version. An 11 MB minified/pretty pair opens, canonicalises and diffs to zero hunks in about 70 ms in a release build — 1.5 s in debug, which is what the test suite pays. Above the 200 MB root-value limit, canonical_lines refuses with TooLarge, so the inline diff reports an error there instead of quietly falling back to raw text.

Part 03Fixing the render loop

Three separate places do work proportional to document size on every recompute, when they only need to do work proportional to the viewport.

Tokenizing every row, always

src/lib/views/compare/components/InlineDiffView.svelteLines 60–62 
const tokenized = $derived.by((): (Token[] | null)[] =>
  rows.map((r) => (r.type === 'gap' ? null : tokenizeJsonLine(r.text)))
);

A 100,000-row diff tokenizes 100,000 lines every time this recomputes. Roughly forty of them are on screen. The fix is one line — map over visibleRows instead of rows, and index the result against startIndex.

This is Pierre's second failure mode verbatim: "work cheap in isolation becomes expensive when repeated thousands of times." Their answer was to defer highlighting to a worker pool and let plain text paint first. Ours is simpler because our tokenizer is cheap — we just have to stop calling it 100,000 times.

Scanning every row for the widest line

maxTextLen at lines 52–58 walks the full row list to find the longest line, so the horizontal scroll region can be sized. Track it as a running maximum while hunks are built instead. Same answer, no full scan.

Rebuilding the world on gap expansion

src/lib/views/compare/components/InlineDiffView.svelteLines 124–131 — expandGap 
const next = rows.slice();              // full array copy
next.splice(rowIndex, 1, ...r.lines);   // splice with spread
rows = next;
anchors = changeAnchors(next);          // full rescan

Two full passes over the document on every click of a context gap. Worse, there's no scroll anchoring — content above the viewport grows and everything the reader was looking at jumps.

Pierre's approach, which we should copy directly: record the first fully visible line plus its offset within the viewport, commit the DOM change, measure what actually changed height, and correct scrollTop so the anchor line stays put. The browser's native scroll anchoring can't do this for us because the mounted DOM changes constantly under virtualization.

The row model, and whether it needs a SumTree

Zed's answer to large-document structure is the SumTree: a B+ tree where every node carries a summary of its subtree, letting you seek by any dimension — byte offset, line number, display row — in O(log n). They use it in more than twenty places, and the rope beneath their text editor is SumTree<Chunk> with 128-character chunks.

Our equivalents are flat and linear:

Location Structure Cost per change
tree-rows.svelte.ts:48 Row[] this.rows.slice() — full array copy on mutation
virtualizer.ts:5 Float64Array buildOffsets — full prefix sum rebuild

Both are O(n) per expand or collapse. A SumTree makes both O(log n).

Measure before building this

Pandia already pages the tree — see tree/logic/paging.ts. If paging keeps the resident row count bounded in the low thousands, an O(n) copy of a few thousand elements is genuinely free and a SumTree would be a large change bought for nothing. Instrument an expand on a multi-million-node array first. Build this only if the number says so.

What we should not build yet

Pierre's Inverse Sticky technique — pinning rendered content to the viewport with negative sticky offsets of (contentHeight - viewportHeight) * -1 — solves blank space appearing during aggressive scrolling on very long documents. It's clever and it preserves native scrolling, but it's a fix for a symptom we haven't observed. They also note Safari still breaks it under heavy scroll. Park it until someone reports blanking.

Part 04Removing the 2 GB cap

The cap isn't arbitrary and it isn't a rendering constraint. It's the point where reading the file into RAM stops being reasonable.

What actually happens on open

src-tauri/src/doc/document.rsLine 251 
let text = std::fs::read_to_string(p)?;   // entire file → heap String

Then, for anything at or above the 10 MB lazy threshold, LazyDoc::new runs FastStr::new(text) — which copies it again. The original String drops afterwards, but the peak is roughly twice the file size. A 2 GB file peaks near 4 GB. That is why the cap sits at 2 and not 4.

There's a second, quieter ceiling underneath it. LazyDoc's array index stores spans as (u32, u32):

src-tauri/src/doc/lazy.rsLines 20–23 
pub struct LazyDoc {
    source: FastStr,
    root_kind: NodeKind,
    root_index: Option<Vec<(u32, u32)>>,   // u32 caps addressing at 4 GiB
}

So even with the memory problem solved, offsets can't address past 4 GiB.

The four changes

  1. Memory-map instead of reading

    Add memmap2 and replace read_to_string with a mapping. The OS pages in only what's touched, so resident memory becomes proportional to what the user actually navigates rather than to file size. Both copies disappear at once.

    This is standard practice for tools in this class — ripgrep and Zed both do it.

    removes the 2× peakmemmap2

  2. Decide how UTF-8 gets validated

    A mapping hands back &[u8]; sonic-rs wants &str. std::str::from_utf8 is one linear SIMD pass, but on a 20 GB file it's still a multi-second stall before anything appears.

    Recommendation: validate up front, on a background thread, reported through the existing CancelFlag in doc/jobs.rs, with a progress state in the UI. Validating lazily per span is faster to first paint but spreads UTF-8 errors across the whole session instead of surfacing them at open, which is worse behaviour for a file the user is about to edit.

    doc/jobs.rsneeds a UI state

  3. Resolve the self-referential borrow

    LazyDoc would need to own the Mmap and hand out &str borrowed from it, which Rust won't allow directly.

    The clean route avoids the crates entirely: validate once in new(), store the Mmap, and expose the text through an accessor tied to &self using from_utf8_unchecked. The unchecked call is sound precisely because construction already proved it. yoke or owning_ref would also work and are safe, at the cost of a dependency and noisier types.

    doc/lazy.rsone unsafe block

  4. Widen the index to u64

    Vec<(u32, u32)> becomes Vec<(u64, u64)>. Index memory doubles from 8 to 16 bytes per root element — a 20M-element array goes from 160 MB to 320 MB of index.

    That is a real cost and worth revisiting later with a segmented index that keeps u32 offsets relative to a chunk base. Not worth it in the first pass.

    removes the 4 GiB address cap2× index memory
The tradeoff we are accepting

A memory-mapped file can change underneath us. If another process rewrites the file while Pandia has it open, the bytes we're reading change with no warning, and in the worst case that's undefined behaviour rather than a clean error. Every editor that mmaps accepts this. We should accept it too, but deliberately, and it belongs in the release notes rather than discovered by a user.

What stays capped, on purpose

Limit Value Keep it?
Whole-document edit EDIT_SIZE_LIMIT — 200 MB Keep. Editing needs the parsed value in memory; that is a genuine requirement, not an artefact.
Root-level getValue GET_VALUE_ROOT_LIMIT — 200 MB Keep. Handing 200 MB across IPC into JavaScript is never the right move.
Lazy threshold LAZY_THRESHOLD_BYTES — 10 MB Keep, and re-measure. It predates mmap and may want to drop once opening is cheap.
Code view SIZE_CAP — 50 MB Revisit. This is a CodeMirror constraint, not ours, and needs its own investigation.

Part 05What we borrowed, and from where

Idea Source Where it lands in Pandia
Tokenize the visible window, not the document Pierre — deferred highlighting via worker pool InlineDiffView.svelte:60
Detach strings so slices stop pinning their parent Pierre — 2.4 GB → 1.15 GB on the Linux diff Solved for free by moving the diff to Rust
Custom scroll anchoring across DOM commits Pierre — CodeView anchoring expandGap, and any future hunk expansion
Checkpoint index plus binary search for line ranges Pierre — replacing linear scans from the start Already present as indexAtOffset in virtualizer.ts
Summary tree for O(log n) seeking by any dimension Zed — SumTree, 20+ uses, rope of 128-char chunks Candidate for the row model — measure first
Render the real old file; don't invent deleted-line rows Zed — split diffs reuse syntax tree and line numbers unchanged Rethinks our UnifiedRow with nullable line numbers
Align two panes with inserted spacers, not merged rows Zed — the block map Split compare view, after the diff moves to Rust

The one that reframes our split view

Our compare view builds a merged row list where each row carries leftNo: number | null and rightNo: number | null. A deleted line is a synthetic object with no right-hand number; an added line is one with no left-hand number.

Zed deliberately rejected that shape. They render the actual old version of the file on the left and highlight the deleted parts, which means line numbers and the syntax tree are reused with no modification and no edge cases to patch. Vertical alignment comes from their block map inserting spacers to pad whichever side is shorter.

It's worth taking seriously, but only after Part 02. The diff has to be cheap and hunk-shaped before the rendering model is worth rearranging around it.

Part 06Order of work

Sequenced so each step makes the next one smaller. The first item is a bug fix; everything after it is capability.

Step What Removes Size
0 Benchmark harness, 32 fixtures, 5 candidates Guesswork about which algorithm to adopt done
1 Visible-window tokenizing The worst per-frame cost ~20 min
2 imara-diff histogram in Rust, hunks over IPC LCS_CELL_CAP, INLINE_MAX, the fake diff 2–3 days
3 Route minified and reformatted pairs to the structural diff — superseded; canonicalisation in step 2 dissolved both shapes (Part 02) Fast, correct, useless answers on both shapes resolved
4 Word-level intra-line diff Nothing — adds the missing feature 1 day
5 Scroll anchoring on gap expansion Content jumping under the cursor half a day
6 mmap, u64 offsets, background validation MAX_DOC_BYTES and the 4 GiB address cap 3–5 days
7 Measure the row model, then decide on a SumTree Possibly nothing — that's the point of measuring 1 day to measure
8 Split view on Zed's model Synthetic deleted-line rows unscoped

Step 1 is worth doing on its own regardless of what happens to the rest. Step 2 is the real unlock and everything downstream assumes it. Step 3 never became work: step 2 shipped diffing canonical renderings rather than raw text, so there is no minified or reformatted pair left to route — the row stays because the reasoning behind it was sound against the old premise. Step 6 is independent of steps 2–5 and can run in parallel if two people are working.

Estimates

These are rough and assume familiarity with both sides of the IPC boundary. Step 6 is the one most likely to grow — the self-referential borrow and the validation-progress UI are both places where the tidy version takes longer than the first working version.
